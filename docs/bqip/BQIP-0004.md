# BQIP-0004: Governance and Activation

```
BQIP: 0004
Title: Governance Model and Protocol Activation
Author: BitQuan Maintainers
Status: Draft
Type: Process
Created: 2025-10-26
```

## Abstract

This BQIP defines the governance model for protocol changes, BQIP approval
process, and activation mechanisms for network upgrades.

## Motivation

Decentralized governance requires clear processes for:
- Proposing protocol changes
- Technical review and approval
- Testnet validation
- Mainnet activation

This BQIP establishes transparent, predictable governance aligned with
Bitcoin's conservative upgrade philosophy.

## Specification

### Governance Structure

```
Maintainers (3+ individuals)
  ↓
Technical Review
  ↓
BQIP Approval (2+ maintainers)
  ↓
Testnet Deployment
  ↓
Mainnet Activation (signaling)
```

### Roles

#### Maintainers

Requirements:
- 2+ years cryptocurrency development experience
- GPG key in repository (docs/security/keys/maintainers/)
- Proven contribution to BitQuan codebase
- Community trust

Responsibilities:
- Review pull requests
- Approve BQIPs
- Sign releases
- Security incident response

Current maintainers: Minimum 3, maximum 7

#### Contributors

Anyone can:
- Submit BQIPs
- Open pull requests
- Review code
- Participate in discussions

### BQIP Process

#### BQIP Types

1. Standards Track: Protocol changes
2. Informational: Design rationale, guidelines
3. Process: Governance, procedures

#### BQIP Lifecycle

```
Draft → Proposed → Active → Final
                  ↓
                Rejected
```

States:
- Draft: Initial proposal, work in progress
- Proposed: Complete specification, under review
- Active: Approved, being implemented
- Final: Implemented and activated
- Rejected: Not accepted

### Approval Requirements

#### Standards Track BQIPs

Requires:
- 2+ maintainer approvals
- No outstanding technical objections
- Reference implementation
- Test vectors
- Testnet deployment (if consensus change)

#### Informational BQIPs

Requires:
- 1+ maintainer approval
- Community feedback addressed

#### Process BQIPs

Requires:
- Majority maintainer approval (>50%)
- Community discussion period (2+ weeks)

### Activation Mechanisms

#### Soft Fork

Changes that tighten rules (backwards compatible with non-upgraded nodes).

Activation process:
1. BQIP approval
2. Implementation in codebase
3. Testnet deployment (minimum 2 weeks)
4. Mainnet deployment with version bit
5. Signaling period (2016 blocks = ~2 weeks)
6. Activation threshold: 95% of blocks signal readiness
7. Lock-in period: 2016 blocks
8. Activation

Example:
```rust
const ACTIVATION_THRESHOLD: usize = 1916;  // 95% of 2016
const SIGNAL_BIT: u32 = 1;  // Version bit for signaling

fn check_activation(last_2016_blocks: &[BlockHeader]) -> bool {
    let signaling = last_2016_blocks.iter()
        .filter(|h| h.version & (1 << SIGNAL_BIT) != 0)
        .count();
    
    signaling >= ACTIVATION_THRESHOLD
}
```

#### Hard Fork

Changes that loosen rules (requires all nodes upgrade).

Activation process:
1. BQIP approval with majority consensus
2. Extended community discussion (3+ months)
3. Testnet deployment (minimum 1 month)
4. Announced activation height
5. Grace period (3+ months notice)
6. Activation at predetermined height

Hard forks are avoided except for critical security issues.

#### Client Update

Non-consensus changes (RPC, P2P improvements).

Process:
1. Pull request review
2. Merge to master
3. Include in next release
4. No activation required

## Emergency Procedures

### Critical Security Vulnerabilities

Process:
1. Private disclosure to maintainers
2. Emergency patch development
3. Coordinated disclosure to miners/exchanges
4. Public release after patch deployment
5. Post-mortem report

### Network Split

If chain split occurs:
1. Halt trading/deposits (exchanges)
2. Identify cause (maintainers)
3. Coordinate resolution
4. Resume normal operations
5. Post-incident review

## Maintainer Management

### Adding Maintainers

Requirements:
- 6+ months active contribution
- Technical expertise demonstrated
- Community nomination
- Existing maintainer approval (2+)
- GPG key commitment

Process:
1. Nomination by maintainer or community
2. Discussion period (2 weeks)
3. Vote by existing maintainers
4. Approval requires 2/3 majority
5. Add to MAINTAINERS file
6. Add GPG key to repository

### Removing Maintainers

Grounds for removal:
- Inactivity (6+ months)
- Violation of Code of Conduct
- Security breach
- Community loss of confidence

Process:
1. Discussion among maintainers
2. Vote requiring 2/3 majority
3. Graceful transition period
4. Update MAINTAINERS file

### Maintainer Rotation

Recommended:
- Review maintainer list annually
- Encourage new maintainer additions
- Support graceful exits
- Maintain 3-7 maintainers

## Decision Making

### Consensus Priority

1. Technical correctness
2. Security
3. Backwards compatibility
4. User experience
5. Performance

### Disagreement Resolution

If maintainers disagree:
1. Extended discussion period
2. Community input
3. Technical working group
4. Vote (simple majority)
5. Document dissenting opinions

### Purpose

- Validate protocol changes
- Test activation mechanisms
- Community testing
- Educational use

### Testnet Resets

Testnet may be reset when:
- Major protocol change
- Accumulated technical debt
- Community consensus

Notice: 2+ weeks before reset
