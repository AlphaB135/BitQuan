# BQIP-0001: PQC Signature Standard

```
BQIP: 0001
Title: Post-Quantum Cryptography Signature Standard
Author: BitQuan Maintainers
Status: Draft
Type: Standards Track
Created: 2025-10-26
```

## Abstract

This BQIP defines the standard for post-quantum cryptographic signatures in
BitQuan, establishing Dilithium3 as the baseline algorithm with provisions
for future algorithm support.

## Motivation

Quantum computers pose an existential threat to current blockchain security.
ECDSA signatures can be broken by Shor's algorithm on a sufficiently powerful
quantum computer. BitQuan adopts NIST-standardized post-quantum algorithms
to ensure 50+ year security resilience.

## Specification

### Signature Algorithm Enum

```rust
enum SigAlgorithm {
    Dilithium3 = 1,  // NIST FIPS 204 (baseline)
    Falcon512 = 2,   // NIST FIPS TBD (future)
    SPHINCS = 3,     // NIST FIPS 205 (future)
}
```

### Dilithium3 Parameters

- Security level: NIST Level 3 (equivalent to AES-192)
- Public key size: 1,952 bytes
- Secret key size: 4,000 bytes
- Signature size: 3,293 bytes (maximum)
- Implementation: pqc_dilithium crate

### Signature Generation

```
signature = Dilithium3.Sign(secret_key, message)

where:
  message = sighash (see transaction.md)
  secret_key = 4,000 byte secret key
  signature = 3,293 byte signature
```

### Signature Verification

```
valid = Dilithium3.Verify(public_key, message, signature)

where:
  public_key = 1,952 byte public key
  message = sighash
  signature = 3,293 byte signature
  valid = true if signature is valid
```

### Key Generation

```rust
use pqc_dilithium::Keypair;

let keypair = Keypair::generate();
let public_key = keypair.public; // 1,952 bytes
let secret_key = keypair.secret; // 4,000 bytes
```

## Transaction Integration

### Witness Structure

```rust
struct Witness {
    signatures: Vec<SignaturePayload>,
}

struct SignaturePayload {
    signer_index: u16,      // Input being signed
    signature: Vec<u8>,     // Dilithium3 signature (3,293 bytes)
    public_key: Vec<u8>,    // Dilithium3 public key (1,952 bytes)
    aux: Option<AuxData>,   // Reserved for future use
}
```

### Signature Hash

```
sighash = SHA256(
    version ||
    network_id ||
    inputs_hash ||
    outputs_hash ||
    lock_time ||
    input_index
)
```

## Validation Rules

1. Signature algorithm must be recognized (currently only 1)
2. Signature length must be <= 4,000 bytes
3. Public key length must be <= 2,000 bytes
4. Signature must verify against sighash
5. Public key hash must match script_pubkey

## Future Algorithms

### Falcon512 (Reserved)

- Security level: NIST Level 1
- Signature size: ~690 bytes
- Faster verification than Dilithium
- Activation: Future BQIP

### SPHINCS+ (Reserved)

- Security level: Configurable
- Signature size: ~7,856 bytes
- Stateless hash-based signatures
- Activation: Future BQIP

## Implementation Guidelines

### Key Storage

Keys should be stored encrypted:

```rust
// ChaCha20-Poly1305 encryption
fn encrypt_key(key: &[u8], password: &str) -> Vec<u8> {
    let salt = random_bytes(32);
    let derived_key = pbkdf2(password, &salt, 100_000);
    chacha20_poly1305_encrypt(key, &derived_key)
}
```

### Signature Caching

Signature verification is expensive (~1ms). Cache results:

```rust
struct VerifiedSignature {
    signature: Vec<u8>,
    result: bool,
    timestamp: Instant,
}

// LRU cache with 10,000 entries
static SIGNATURE_CACHE: Lazy<Mutex<LruCache<[u8; 32], VerifiedSignature>>> = ...;
```

### Batch Verification

Dilithium does not support native batch verification. Verify signatures
in parallel:

```rust
fn verify_batch(sigs: Vec<(PublicKey, Message, Signature)>) -> Vec<bool> {
    sigs.par_iter()
        .map(|(pk, msg, sig)| pk.verify(msg, sig))
        .collect()
}
```

## Security Considerations

### Quantum Resistance

Dilithium3 provides NIST Level 3 security:
- Classical security: 192 bits
- Quantum security: 192 bits
- Resistant to Grover's algorithm
- Resistant to Shor's algorithm

### Side-Channel Resistance

Implementations must be constant-time:
- No timing leaks during signing
- No timing leaks during verification
- Masked arithmetic for secret operations

### Key Reuse

Unlike ECDSA, Dilithium allows key reuse. However:
- Generate unique keys per wallet for privacy
- Rotate keys periodically (recommended)
- Use HD wallet for key derivation

## Backwards Compatibility

This is the initial signature standard. No backwards compatibility issues.

Future algorithm additions will:
1. Maintain support for Dilithium3
2. Allow mixed transactions (different algorithms)
3. Require network upgrade (soft fork)

## Reference Implementation

```rust
// crates/crypto/src/dilithium.rs
use pqc_dilithium::{Keypair, PublicKey};

pub fn sign(secret_key: &[u8], message: &[u8]) -> Vec<u8> {
    let keypair = Keypair::from_bytes(secret_key);
    keypair.sign(message).to_vec()
}

pub fn verify(public_key: &[u8], message: &[u8], signature: &[u8]) -> bool {
    let pk = PublicKey::from_bytes(public_key);
    pk.verify(message, signature)
}
```
