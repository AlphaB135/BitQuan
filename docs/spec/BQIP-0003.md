# BQIP-0003: Wallet and Ecosystem Standards (PQC PSBT, Addressing, SDK)

- Author: BitQuan Core <dev@bitquan.org>
- Status: Draft
- Type: Standards Track
- Created: 2025-10-25

## Abstract
Specifies PQC‑capable PSBT extensions, address formats, and SDK interfaces to enable wallets, exchanges, and tooling for BitQuan.

## Motivation
Achieve smooth ecosystem adoption by standardizing how keys, addresses, transactions, and signatures are represented and exchanged.

## Specification
### 1. Addressing (Bech32m‑style, TBD details)
- HRP: "bq" (mainnet), "tbq" (testnet).
- Witness version: v0 (reserved for simple single‑sig PQC).
- Payload: 20‑byte pubkey hash (HASH160 of PQC pubkey) for P2PQC‑PKH.
- Script template: `OP_DUP OP_HASH160 <20B> OP_EQUALVERIFY OP_CHECKSIG_PQC`.

### 2. PSBT(PQC) Extensions
- Define new key types for PQC public keys and signatures (e.g., `psbt_in_pqc_sig`, `psbt_out_pqc_pubkey`).
- Serialization uses CompactSize length prefixes; signatures are raw bytes of the chosen scheme (e.g., Dilithium3).
- SigAlgorithm field mirrors BQIP‑0001 enum; unknown values MUST be rejected by default.

### 3. Key Material and Derivation
- Mnemonic: BIP‑39 compatible mnemonics allowed; seed to PQC master key via HKDF‑SHA256 domain separation.
- Derivation paths: purpose' / coin_type' / account' / change / address_index (SLIP‑44 coin_type TBD).
- Strong zeroization and constant‑time operations are REQUIRED in SDKs.

### 4. SDK Interfaces
- Rust crate and TypeScript package providing: address encode/decode, PSBT creation/signing, transaction build/serialize (per BQIP‑0001).
- FFI boundary types must avoid secret copying; expose signing contexts with limited lifetime.

### 5. Exchange/Node Integration
- JSON‑RPC fields for PQC signatures and algorithms.
- Deposit/withdrawal address validation rules and test vectors.
- PSBT round‑trip tests between SDK and node.

## Rationale
- Bech32m improves error detection; HRP separation avoids cross‑chain confusion.
- PSBT extensions minimize bespoke flows and enable hardware wallet support.

## Backwards Compatibility
New definitions; no legacy users. Future multi‑sig/script upgrades will use new descriptors and PSBT keys.

## Security Considerations
- Enforce SigAlgorithm allow‑list; reject unknown/experimental schemes by default.
- Protect mnemonic/seed at rest; offer air‑gapped signing flows where possible.

## Test Plan
- Cross‑language vectors for address encoding/decoding.
- PSBT fixtures containing PQC keys/sigs; negative tests for wrong algo/lengths.
- Fuzzing of parser/serializer; constant‑time audits.
